# H3.9.2 Implementation Contract — R3

## Objective

Expand the five core H3.5–H3.9 benchmarks to fixed H3.9.2 limits, with campaign-global source/family/fingerprint-disjoint final holdouts frozen before tuning. H4 remains closed until both the benchmark and architecture gates pass.

## Non-goals

- no H4 implementation;
- no M3 architecture expansion;
- no synthetic qualification evidence;
- no threshold changes after holdout inspection;
- no holdout-driven tuning;
- no plaintext final-holdout labels on the developer/tuning surface.

## Pre-registered cardinalities

- H3.5: 300 = 150 / 60 / 90.
- H3.6: 240 = 120 / 48 / 72.
- H3.7: 200 = 100 / 40 / 60.
- H3.8: 240 = 120 / 48 / 72.
- H3.9: 300 = 150 / 60 / 90.

## Source partition and curation quotas

`config/curation-plan.json` fixes the global source partition before curation. Six of 18 eligible source works are reserved globally for holdout use; the other twelve are non-holdout sources. A source cannot be holdout in one benchmark and tuning material in another.

`config/curation-quotas.json` deterministically allocates all 1,280 cases across those pools before case selection. Validation recomputes the quota plan and rejects drift. For multi-source identity benchmarks, all sources used by a case/family graph must belong to one partition.

## Provenance contract

Every qualification case records all source works, not just a primary source. Every source reference has an exact excerpt and source blob pin. The curation step requires the excerpt to occur verbatim in a locally acquired source whose Git blob SHA matches the registry.

`reference_pilot` requires a source verification and at least one reviewer. `expert_gold` requires two distinct reviewers plus an independent adjudicator. Synthetic records are rejected.

## Sealed final holdout

Final-holdout plaintext gold is prohibited in `benchmarks/*/records.jsonl`. `build-splits` encrypts holdout gold using AES-256-GCM with a 256-bit external key and replaces the public payload with `gold_sealed=true`. The encrypted record is cryptographically bound to the public case identity, normalized input fingerprint, complete source set, family ID, and gold status.

The key is never stored in the repository or freeze. The ciphertext is frozen. `evaluate-holdout` requires both a verified freeze and matching `MODEL_LOCK.json`, then uses the external key to decrypt only for final scoring. Wrong keys, modified ciphertext, changed public bindings, or post-access prediction changes fail closed.

After sealing, in-repository staging is sanitized to remove final-holdout plaintext gold. Any curator-private pre-seal copy is outside the developer/tuning trust boundary.

## Freeze boundary

Before freeze, acquisition, curation, adjudication, provenance repair, and split-feasibility repair are permitted. Once `FREEZE_MANIFEST.json` is emitted, the specification, records, sealed ciphertext, source registry, source partition, curation quotas, schemas, evaluator, validator, splitter, sealing code, lifecycle logic, and gate logic are hashed into the freeze.

The freeze cannot be overwritten. A defective frozen benchmark must be invalidated and replaced by a new version/freeze.

## Post-freeze protocol

Only development and validation are exported to the tuning pack, and export requires a verified freeze. A candidate is then pinned in `MODEL_LOCK.json`. Holdout evaluation refuses to run without that lock and the external holdout key.

The first final evaluation creates `HOLDOUT_ACCESSED.json`, binding freeze ID, model-lock hash, prediction hashes, ciphertext hashes, and the non-secret key identifier. Different predictions cannot be evaluated again under the same freeze. Byte-identical replay is allowed for reproducibility.

## Benchmark gate

`benchmark_gate_passed` is true iff:

1. all five expanded datasets qualify;
2. benchmark-local and campaign-global disjointness checks pass;
3. the sealed stores bind correctly to the public holdout records;
4. the freeze verifies;
5. the final evaluation is produced by the evaluator under the same freeze/model lock/sealed stores;
6. the holdout access marker matches that report and prediction set; and
7. all preregistered benchmark thresholds pass.

`h4_entry_allowed` remains the derived conjunction of benchmark and independent architecture gates.
